# Expanded Bedrock guardrail and shared-helper receipt-download tool

Two independent features land on this branch. FEAT-001 (commit `d4b41d9`) widens the `AssistantGuardrail` CfnGuardrail to the full feature surface the installed aws-cdk-lib 2.160.0 supports: six content filters, a word policy, an expanded PII/regex policy, three DENY topics, and contextual-grounding filters. FEAT-002 (commit `7ebc27a`) adds an Option-A receipt-download capability: a `get_receipt_url` Strands tool that reuses the presign Lambda's signing code through one shared helper, surfaces the URL through the `req_ctx` side channel into a top-level `receipt` envelope, grants the assistant role a narrow `s3:GetObject`, and renders a download link in the SPA. Both features are verified green locally.

Watch for: nothing blocking. The one `npm test` failure (`raw Bedrock invocation-logging config`) is the pre-existing, out-of-scope baseline failure and is unchanged (confirmed). PROMPT_ATTACK synthesizes with OutputStrength NONE and `tierConfig` is absent (confirmed).

**Verdict**: APPROVED

## High-level view

The guardrail change is a pure L1 widening that stays inside what the pinned CDK version exposes. The author verified `tierConfig` is not a key on `ContentPolicyConfigProperty` in 2.160.0 and deliberately omitted it; synth confirms it never appears in the template, and PROMPT_ATTACK carries the input-only OutputStrength NONE that Bedrock requires. The published `CfnGuardrailVersion` and the `guardrailId`/`guardrailVersion` cross-stack contract are untouched (still exactly one GuardrailVersion resource).

The receipt tool centralizes the SigV4 + regional-endpoint S3 client in `presign.handler.make_s3_presign_client`, and both the presign Lambda and the tool build URLs through the single `generate_url`. There is exactly one copy of the signing configuration (`signature_version="s3v4"` lives only in `presign/handler.py`). The presign security model — 15-minute SigV4 regional GET for `receipts/{orderId}.pdf` only, order-id validated — is carried over unchanged.

Trust boundary: the URL only ever reaches the client through the authoritative `req_ctx['receipts']` side channel and the `build_response` envelope, never parsed from model text. A unit test asserts the envelope ignores a decoy URL in the reply text. The assistant role gets a scoped `s3:GetObject` on the receipts object ARN; `kms:Decrypt` is already covered by the existing `grantEncryptDecrypt`, so no new KMS grant was added.

### Guardrail widening stays inside the pinned CDK surface

The risk with widening an L1 construct is adding a key the installed version does not model, which would surface as a tsc error or a synth-time rejection. The author pinned the work to aws-cdk-lib 2.160.0 and deliberately skipped `contentPolicyConfig.tierConfig` because `ContentPolicyConfigProperty` in that version carries only `filtersConfig`. `tsc --noEmit` is clean and `grep` of the synthesized template finds zero occurrences of `TierConfig` (confirmed). PROMPT_ATTACK is the one filter that cannot carry an output strength; the template synthesizes it as `InputStrength: HIGH / OutputStrength: NONE` (confirmed), matching the Bedrock rule.

The published-version contract is intact: the synthesized SecurityData template has exactly one `AWS::Bedrock::GuardrailVersion`, and `guardrailId`/`guardrailVersion` remain `public readonly` members sourced from `guardrail.attrGuardrailId` and `guardrailVersion.attrVersion` (confirmed). A redeploy publishing a new version is expected per the feature spec.

### One signing helper, reused by Lambda and tool

The SigV4 + regional-addressing client config moved out of the Lambda `handler()` into `make_s3_presign_client(region)`, and the Lambda now calls it. `tools.get_receipt_url` imports `presign.handler` defensively (guarded, so the module still imports without boto3) and builds its client and URL from the same `make_s3_presign_client` + `generate_url`. `grep signature_version` across `app/` matches only `presign/handler.py` (confirmed), so there is a single copy of the signing configuration and the 15-minute (`EXPIRES_IN=900`) regional GET for `receipts/{orderId}.pdf` is shared verbatim.

### Receipt URL rides the side channel, not model text

`get_receipt_url` validates the order id with `pii.validate_order_id` (REJECTED appends nothing), optionally confirms existence via the orders table (NOT_FOUND), then appends `{orderId, url, expiresIn}` to `req_ctx['receipts']` and returns OK. `build_response` emits a top-level `body['receipt']` from `req_ctx['receipts'][-1]` only when non-empty, mirroring the existing `pendingRefund`/`placedOrder` pattern. `test_build_response_receipt_from_side_channel` passes a decoy URL in the reply text and asserts the envelope uses only the side-channel record — the trust boundary is enforced and tested.

### IAM and env grants

The AssistantFn environment gains `RECEIPTS_BUCKET` and the assistant role gains a `ReadReceipts` `s3:GetObject` statement scoped to `receiptsBucket.arnForObjects('*')`; both appear in the synthesized AppEdgeAI template (confirmed). The author correctly notes `kms:Decrypt` is already granted via `kmsKey.grantEncryptDecrypt(assistantRole)`, so no additional KMS grant is needed for the CMK-encrypted bucket.

### SPA rendering

`renderReceipt` builds the link with `createElement` + `textContent` and sets `href` from the opaque server-supplied URL, with `target="_blank"` and `rel="noopener"` — no `innerHTML` interpolation of untrusted values. `sendMessage` invokes it only when `data.receipt && data.receipt.url`. `node --check spa/app.js` is clean.

### Test coverage

Python is at 49 tests, all green (baseline was 45; +4 for the receipt tool and envelope). New tests cover: valid id -> OK + populated side channel; invalid id -> REJECTED + empty side channel; envelope present only when the side channel is non-empty; envelope ignores decoy URL in reply text. The injected `make_s3_presign_client` monkeypatch keeps the tests boto3-free.

Not tested: the NOT_FOUND path (orders-table-bound, missing item) has no unit test; the spec treats format validation as the minimum guarantee, so this is a gap rather than a defect. The `generate_url` error branch inside the tool (`err is not None`) is also only indirectly covered.

### Baseline invariant

`npm test` fails exactly one assertion, `raw Bedrock invocation-logging config on CMK-encrypted destinations`, which the context file documents as pre-existing and out of scope (the stack provisions logging via an AwsCustomResource, not a CFN resource). No other assertion regressed; the extended Guardrail assertion and the published-version assertion both pass (confirmed).
