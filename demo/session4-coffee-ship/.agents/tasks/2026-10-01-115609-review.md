# Standalone coffee-ship DVA-C03 testing-and-deployment demo

Scaffolds a self-contained, deployable AWS demo under `demo/session4-coffee-ship` that teaches the DVA-C03 "Testing and Deployment" domain through a coffee-shop ordering app: CDK v2 infra split into a network/data stack and an app/pipeline stack, a SAM Python 3.12 Lambda shipped via a CodeDeploy canary, an ECS/Fargate container path behind an ALB, an S3-source CodePipeline with a manual approval gate, plus teaching artifacts, a Kiro hook, scripts, and docs. The whole build is verified locally only (synth, pytest, bash -n, JSON/YAML parse) and never deploys. The region ap-southeast-1 is pinned across the CDK env, samconfig, both scripts, and the runbook.

Watch for: nothing blocking. The SAM template and the CDK network stack both declare name-identical `coffee-ship-orders` SQS/DynamoDB resources — this is an intentional "declare the same thing more than one way" teaching device, documented in the README, not a collision bug (confirmed). The standalone `appspec.yaml` is a teaching artifact; the actual Lambda traffic shift is driven by the SAM `DeploymentPreference`, which is the real mechanism (confirmed).

**Verdict**: APPROVED

## High-level view

The infra is cleanly split: `NetworkDataStack` owns the VPC (public subnets only, zero NAT gateways), DynamoDB, SQS, SSM parameter, Secrets Manager secret, and AppConfig app/env/profile/strategy; `AppPipelineStack` owns ECR, the Fargate+ALB service, the SNS approval topic, a CloudWatch alarm, and the pipeline. Props flow one way from network to pipeline. Synth is clean and the synthesized templates contain every required feature.

The release path is an S3-source CodePipeline — Source(S3) → Build(CodeBuild) → Deploy-Test(S3) → Approval(Manual/SNS) → Deploy-Prod(S3) — with no GitHub or CodeCommit anywhere in the synthesized output. The CodeBuild stage runs `sam validate` (guarded for a missing CLI), `pytest`, and a documented no-op headless gate that exits 0 but is annotated to fail-on-nonzero in a real pipeline.

Two safe-deploy strategies are demonstrated side by side: the Lambda canary (`Canary10Percent5Minutes` with a CloudWatch error alarm wired into `DeploymentPreference.Alarms` for automatic rollback) and the ECS rolling update (deployment circuit breaker with rollback, 100/200 health percents).

Cost discipline is real and consistent: public subnets with no NAT, 256/512 Fargate at desiredCount 1, ECR lifecycle keeping 10 images, pay-per-request DynamoDB. The scripts pin the region, use `set -euo pipefail`, resolve the auto-named source bucket from stack resources rather than hardcoding, and `destroy.sh` guards every destructive step behind a typed `destroy` confirmation.

The known gaps are all intentional and documented: duplicate orders-resource names across the SAM and CDK stacks (the teaching point), the appspec as an inspectable artifact rather than the live mechanism, and the headless gate as a placeholder. No forbidden reads or imports from `applications/` or `demo/session3` exist anywhere under the project root.

## Standalone boundary and region pinning

A grep for `applications` and `session3` across the whole project returns no matches, so the demo imports and reads nothing from the forbidden paths — it stands alone under its own root. The region ap-southeast-1 is pinned in `infra/bin/coffee-ship.ts` (the single `env` applied to both stacks), `app/samconfig.toml`, `deploy.sh`, `destroy.sh`, and the runbook, and it appears in both synthesized templates. There is no second region referenced anywhere.

## Infra split and network/data stack

`NetworkDataStack` exposes `vpc`, `ordersQueue`, and `ordersTable` as readonly props that `AppPipelineStack` consumes through a typed `AppPipelineStackProps` interface — a one-way dependency with no cross-stack cycles. The synthesized network template contains exactly one each of the AppConfig Application, Environment, ConfigurationProfile, and DeploymentStrategy, the Secrets Manager secret, the SSM parameter, the DynamoDB table, and the SQS queue, and zero NAT gateways (public-subnet-only VPC).

## S3-source pipeline, no GitHub/CodeCommit

The synthesized pipeline template shows the Source action with `Owner: AWS, Provider: S3`, Build as `CodeBuild`, two S3 deploy actions, and a `Manual` approval action — and zero matches for GitHub or CodeCommit. The five stages render in order (Source, Build, Deploy-Test, Approval, Deploy-Prod), the source object key is `source.zip` in a versioned bucket, and the manual approval is wired to the `coffee-ship-approval` SNS topic. The source bucket is auto-named, and both scripts resolve it from stack resources rather than hardcoding, which is the correct pattern for a CDK-generated bucket name.

## Build gate behavior

The buildspec runs `sam validate --lint` only when the SAM CLI is present (a missing CLI is a non-fatal skip, a present CLI reporting a real error fails the stage), then `pytest`, then the headless gate. The headless gate runs `kiro --headless --prompt "review the deploy log" || true` followed by `exit 0`, with an inline comment stating that removing `|| true` makes a non-zero exit fail the stage. The gate is a deliberate no-op: a reviewer should note that in the current form the pipeline Build stage cannot fail on the headless check, by design, until the `|| true` is removed.

## Lambda canary with alarm rollback

The SAM template sets `AutoPublishAlias: live` and `DeploymentPreference.Type: Canary10Percent5Minutes` with `Alarms: [LoyaltyErrorsAlarm]`. The alarm (`coffee-ship-loyalty-errors`) watches `AWS/Lambda Errors` on the live alias with threshold 1, so a spike during the canary window triggers CodeDeploy rollback. Runtime is python3.12, handler `app.handler`, with both an SQS event source and a POST `/orders` API event. The handler parses the API Gateway proxy body as a JSON **string** and returns 400 on a non-string, non-JSON, non-object, or missing-total body — the malformed test event exercises exactly that path.

The standalone `appspec.yaml` declares the Lambda target with Before/AfterAllowTraffic hooks and `<CURRENT_VERSION>`/`<TARGET_VERSION>` placeholders. In a SAM-managed canary SAM generates the appspec from the `DeploymentPreference` at deploy time, so this file is an inspectable teaching artifact rather than the live driver — a reader should not expect editing it to change deployment behavior. It satisfies the task's "appspec.yaml + taskdef" requirement.

## ECS/Fargate container path

The synthesized app template shows `Cpu: "256"`, `Memory: "512"`, `DesiredCount: 1`, `MaximumPercent: 200`, `MinimumHealthyPercent: 100`, and a `DeploymentCircuitBreaker` with `Enable: true` / `Rollback: true`. The service runs in public subnets with `assignPublicIp` and a placeholder public image until the pipeline publishes to the `coffee-ship` ECR repo, whose lifecycle policy keeps the 10 most recent images (`imageCountMoreThan 10 → expire`). The container app is stdlib-only Python on port 8080, matching the taskdef portMapping and the ALB target.

## Teardown safety

`destroy.sh` prints a warning listing every resource it will delete, then requires the operator to type `destroy` before any destructive action runs. It deletes the SAM stack if present, empties the versioned pipeline buckets (current objects plus versions and delete-markers), batch-deletes ECR images, and runs `cdk destroy --all --force`. Each step is guarded by an existence check so re-runs are safe. Both scripts use `set -euo pipefail` and parse under `bash -n`.

## Teaching artifacts and Kiro hook

The reference set declares the same `coffee-ship-orders` queue three ways (raw CloudFormation JSON, a CDK TS construct, and a SAM YAML resource), all with matching queueName, 60s visibility timeout, and 4-day retention mirroring the real `OrdersQueue`, with a README stating none are deployed. The Kiro hook is a v1 schema file: `version "1"`, `enabled true`, `when.type PostFileSave` with a `\.py$` pattern, and `then.type agent` whose prompt restricts the agent to adding/updating tests without editing source.

## Test coverage

`pytest` passes 5 tests: the API happy path (string body → 200 with floored points), the malformed body (→ 400), `compute_points` flooring, `compute_points` rejecting a missing total, and the SQS multi-record path.

Not tested: the container HTTP service (`container/app.py`) has no unit tests — it was smoke-tested manually per the FEAT-003 findings but has no automated coverage, so its 400/404/health routing isn't exercised in CI. Acceptable for a teaching demo, but worth noting.

Reproduced all verification independently: `pytest` → 5 passed; `bash -n` on both scripts → clean; container app compiles; all JSON (events, taskdef, cfn.json, hook) parses; hook matches the v1 schema; the happy event body is a string; all YAML parses under a permissive SAM-tag loader. `npm install` + `cdk synth` (with a dummy account) exits 0 with only informational CDK notices, and the synthesized templates contain every required construct. No AWS deploy was attempted, matching the local-only mandate.
